# 로그인 + 로깅 인프라 + 탭 정리 — 설계 스펙 (Spec 1)

- **작성일**: 2026-05-20
- **대상 파일**: `index.html` (단일 HTML 프로토타입)
- **범위**: A(로그인·로깅 인프라) + B(탭 정리) + 색상 실험실 task 설계(trial 로깅 reference 구현)
- **후속 spec**: C(소리 탐험실), D(거문고 안족 가시화), E(화음 감상실 2단계) — 별도 문서

## 1. 목적

학습자가 로그인하여 학습 로그를 수집할 수 있도록 앱을 재설계한다. 수집한 로그로부터 초6 학습자의 **비례 추론 이해가 변화하는 양상**을 microgenetic method로 분석하는 것이 연구 목표다. 단, **앱이 돌아가는 것이 최우선** — 로깅은 어떤 경우에도 앱을 멈추거나 느리게 해서는 안 된다.

## 2. 분석 방법론 토대 — Microgenetic Method

로그 스키마는 분석 방법론에서 역산한다(analysis-driven logging). 기준은 Siegler & Crowley(1991), Siegler(2006)의 microgenetic method다.

### 2.1 세 가지 핵심 조건

| 조건 | 의미 | 로그에 대한 요구 |
|---|---|---|
| ① 변화 기간 전체 포괄 | 안정된 출발점→안정된 도달점까지 관찰 | `userCode`로 여러 회기 세션을 종단 연결 |
| ② 높은 관찰 밀도 | 변화율보다 관찰 빈도가 촘촘 | 정답/오답뿐 아니라 도달까지의 **중간 상태 trajectory** 기록 |
| ③ 시도별 집중 분석 | trial 단위로 변화 과정을 추론 | 로그의 기본 단위 = **trial(시도)** |

### 2.2 변화의 5차원과 데이터 요구

- **Path(경로)**: 전략 순서의 변화(예: 색상 `2:3→3:4` 가법 → `2:3→4:6` 승법). → 시도별 전략 분류 가능한 trajectory.
- **Rate(속도)**: 며칠/몇 회기에 걸친 변화. → 종단 sessionId 연결.
- **Breadth(폭)**: 한 영역의 전략이 다른 영역으로 전이되는지. → **동일 비율을 여러 탭에 의도 배치**(C/D/E task 설계 숙제).
- **Variability(변동성)**: 한 회기 안에서도 전략을 오가는지. → 한 세션에 같은 유형 task 다중 trial.
- **Source(원천)**: 변화 촉발 요인(발견/오답/힌트). → reveal·hint·error 이벤트를 transition과 시간적으로 인접 기록.

### 2.3 전략 분류 정책

앱은 **전략을 단정하지 않는다.** trajectory·outcome·trigger의 raw 재료를 빠짐없이 남기고, 전략 코딩은 연구자가 사후(post-hoc)에 규칙/수작업으로 수행한다. Siegler 본인도 trial-by-trial을 사람이 코딩한다. 앱의 책임은 "분류에 필요한 재료를 잃지 않는 것"이다.

## 4. 로그 데이터 모델

### 4.1 계층

```
session  ──< trial ──< event
```

- **session**: 한 번의 로그인~이탈. 학생/단말/시각 메타.
- **trial**: 하나의 task 시도. microgenetic 분석의 기본 단위.
- **event**: trial 내부 또는 세션 수준의 개별 사건.

### 4.2 공통 필드 (모든 레코드)

```
schemaVersion   "1"
sessionId       세션 UUID
userCode        예: "603-12"
userName        학생 입력 이름
clientTs        클라이언트 ISO 시각 (밀리초)
seq             세션 내 단조 증가 시퀀스(순서 보장·중복 제거)
```

### 4.3 session 레코드 (sessions 시트)

```
sessionId, userCode, userName, codeValid(서버판정),
startTs, endTs, userAgent, screen, lang, appVersion(git short hash)
```

### 4.4 trial 레코드 (trials 시트)

```
trialId         trial UUID
sessionId, userCode, userName
tab             color | sound | instrument | harmony
activityId      예: "color.equalize"
taskId          구체 과제 식별자 (예: "color.equalize.target_2_3")
attemptNo       같은 task의 몇 번째 시도인가 (1부터)
startTs, endTs
trajectory      JSON 배열 — [{t, state}, ...] 거쳐간 의미있는 중간 상태
outcome         correct | wrong | abandoned | open(자유탐색)
finalState      JSON — 최종 상태
triggerRef      직전 발견/힌트/오답 eventId (있으면)
```

`trajectory`는 **debounce된 "머문 상태"**만 담는다(드래그 raw 아님): 상태가 바뀌고 **400ms 이상 정지**하면 1개 포인트로 push. 이로써 조건②(밀도)를 만족하되 데이터 폭증을 막는다.

### 4.5 event 레코드 (events 시트)

`eventType` 분류(변화 양상 위주):

- **session**: `login`, `resume`, `heartbeat`(2분), `unload`
- **navigation**: `tab_enter`, `tab_leave`, `stage_change`
- **trial**: `trial_start`, `trial_state`(머문 상태), `trial_submit`, `trial_reset`
- **discovery**: `reveal`(비밀 풀기), `blind_toggle`, `hint`
- **outcome**: `correct`, `wrong`, `abandon`
- **error**: `client_error`(전역 onerror 후킹) — 단 전송 실패해도 앱 무영향

```
eventId, trialId(해당시), eventType, payload(JSON), + 공통필드
```

수집하지 않는 것: 개별 mousemove, 매 슬라이더 tick, PII(이름 외 개인정보), IP. → 데이터량·프라이버시·앱 성능 보호.

## 5. 클라이언트 아키텍처

### 5.1 모듈 (index.html 내 단일 IIFE `Logger`)

```
Logger.init({endpoint, token, appVersion})
Logger.setUser({code, name})
Logger.startTrial({tab, activity, task}) → trialId
Logger.trialState(trialId, state)        // 400ms debounce 내부 처리
Logger.endTrial(trialId, {outcome, finalState})
Logger.event(type, payload)              // 동기 즉시 반환
Logger.flush()                           // 강제 전송 (unload 시)
```

### 5.2 핵심 불변식 (앱 안정성 최우선)

1. **`logEvent` 류는 절대 await 없음** — 메모리 큐에 push하고 즉시 반환. 어떤 호출자도 블로킹되지 않음.
2. **모든 로깅 호출은 try/catch로 감싸 silent** — 로깅 내부 예외가 앱 로직으로 새지 않음.
3. **큐는 메모리 + localStorage 이중**. push 시 메모리에 넣고 주기적으로 localStorage 백업 → 새로고침/크래시에도 유실 최소화.
4. **전송은 배치**: 10건 누적 또는 5초 경과 시 `fetch` POST. 실패하면 지수 backoff 재시도(최대 N회), 끝까지 실패하면 localStorage에 잔존시키고 다음 기회에 재전송.
5. **localStorage 용량 가드**: 큐가 상한(예: 500건/1MB)을 넘으면 가장 오래된 것부터 버리되, 버린 개수를 카운터로 남김(`dropped`). 데이터가 앱을 멈추게 두지 않는다.
6. **전송 방식**: 평상시 `fetch(keepalive:false)`, `unload`/`visibilitychange:hidden` 시 `navigator.sendBeacon`으로 마지막 flush.

### 5.3 CORS 메모

Apps Script Web App에 브라우저에서 직접 POST 시 preflight를 피하려고 **`Content-Type: text/plain`** 으로 보내고 본문은 JSON 문자열로 직렬화한다(Apps Script가 `e.postData.contents`를 파싱). 응답 헤더에 CORS 허용을 설정.

## 6. Apps Script + Sheets 인터페이스

### 6.1 엔드포인트

```
doPost(e):
  - e.postData.contents → JSON.parse → { token, records:[...] }
  - token 불일치 → 무시(200 반환, 봇 차단)
  - records를 type별로 sessions/trials/events 시트에 append
  - codeValid: roster 시트에서 userCode 조회해 판정값 기록
  - 반환: {ok:true, accepted:n}
doGet(e):
  - 헬스체크용 {ok:true} (선택)
```

배치 append는 `sheet.getRange(...).setValues(2D)`로 한 번에 — 행별 append보다 빠르고 quota 절약.

### 6.2 Sheets 구조

- `sessions`, `trials`, `events` — 4장의 스키마대로 헤더 행 고정
- `roster` — 사전 발급 코드 명단 (코드, 학년, 반, 번호) → codeValid 판정·분석 join
- 분석: 피벗테이블, `QUERY()` 함수, 차트로 직접. 필요 시 BigQuery/스프레드시트 내보내기.

### 6.3 비밀 토큰

`token`은 약한 봇 차단용(공개 클라이언트라 완전 비밀 불가). 진짜 데이터 무결성은 사후 `roster` join + `codeValid` 플래그 + 형식 검증으로 확보.

## 7. 로그인 UI/UX

### 7.1 흐름

```
앱 첫 진입
  → localStorage에 유효 세션 있나?
     예 → 자동 resume (이름·코드 표시, "내가 아니에요" 버튼)
     아니오 → 로그인 모달
        입력: [코드] [이름]
        형식 검증 통과 → 입장 + login 이벤트
        형식 불일치 → 인라인 안내(차단)
앱 우상단: 현재 사용자 칩 + "사용자 변경"(로그아웃)
```

### 7.2 코드 형식

정규식 예: `^\d{1,2}-\d{1,2}-\d{1,2}$`(학년-반-번호) 또는 운영 편의를 위한 단순형 — **정확한 형식은 사용자(연구자) 확정 필요**. 형식만 맞으면 입장, 서버가 roster 대조해 `codeValid`만 표시.

### 7.3 동의 고지

연구 데이터 수집임을 알리는 한 줄 고지 + (필요 시) 보호자/학교 동의는 **연구 프로토콜/IRB 사안** — 문구는 사용자 확정. 로그인 모달에 고지 자리를 마련해 둔다.

## 9. 색상 실험실 Task 설계 (trial 로깅 reference)

현재 색상 실험실은 자유 탐색 + "같은 색 발견" 구조다. UI/기능은 그대로 두고 그 위에 **명시적 task 레이어**를 얹어 trial 로깅을 정식화한다(`col` 객체에 이미 있는 `interactions/dragLog/strategy`를 Logger로 승격).

### 9.1 Task 유형

- **자유 탐색** (`color.explore`): 기존 그대로. trial outcome=`open`. 학생이 만든 색·양 trajectory만 수집(baseline 변동성·전략 관찰).
- **등가비 재현** (`color.equalize`): 기준 색을 제시하고 "같은 색을 **다른 양**으로 만들기". microgenetic 핵심 task.
  - 예: 기준 빨강:파랑 = 2:3 제시 → 학생이 총량을 바꿔 같은 색 재현.
  - **가법 전략**(2+k:3+k)과 **승법 전략**(2k:3k)이 trajectory에 그대로 드러남 → path/source 분석.
  - 여러 기준 비(2:3, 1:2, 3:4 등)로 다중 trial → variability.

### 9.2 trial 매핑

```
startTrial({tab:'color', activity:'color.equalize', task:'target_2_3'})
  → 학생이 색 부을 때마다 trialState({r,y,b, rgb})   // 400ms debounce
  → 같은 색 판정 시 outcome='correct', reveal 클릭 시 triggerRef 연결
  → endTrial(outcome, finalState)
```

"같은 색" 판정 임계(RGB 거리)와 task 제시 UI(기준 색 칩, 미션 배너)는 구현 단계에서 확정. 색상의 정밀 task 카탈로그(기준 비 목록·난이도 순서)는 사용자와 추가 논의 가능.

## 10. 데이터량·안정성 분석

- 1 trial ≈ trajectory 5~15 포인트 + 시작/종료 이벤트 ≈ 2~4KB JSON.
- 한 회기(40분) 학생당 trial 20~40개 가정 → 세션당 ~100KB 미만. 30명 동시 → 배치 전송으로 무리 없음.
- 모든 mousemove를 보냈다면 10~100배 — 그래서 debounce·trial 모델로 절감.
- 네트워크 단절·서버 장애 시: 큐가 localStorage에 쌓이고 앱은 정상. 복구되면 재전송. 상한 초과분만 drop(카운트 기록).

## 11. 한계 (정직하게)

1. 전략 자동 분류는 휴리스틱 한계 — 최종 코딩은 사후 수작업. 앱은 raw 재료 보존만 보장.
2. 종단성(path/rate)은 운영에 의존 — 같은 학생이 같은 코드로 여러 회기 들어와야 성립. 회기 설계는 연구 프로토콜 결정사항.
3. Breadth(전이) 분석은 C/D/E task에 동일 비율을 의도 배치해야 성립 — 인프라만으론 불충분.
4. 공개 클라이언트라 토큰은 약한 차단 — 데이터 무결성은 roster join·codeValid·형식검증으로 보완.
5. localStorage 의존 — 시크릿 모드/저장소 차단 환경에선 종단·재전송 보장 약화(그래도 앱은 동작, 메모리 큐로 best-effort 전송).

## 12. Spec 1 범위 밖 (후속)

- **Spec C — 소리 탐험실**: 물의 양으로 소리 변화 탐험 → 도레미파솔라시도(8음) 만들기.
- **Spec D — 악기 제작실**: 펜플룻 + 거문고. 거문고는 **안족(가동 브리지)을 실제로 보이게** 하고 누르는 느낌의 인터랙션.
- **Spec E — 화음 감상실**: 1단계(기본음 도 vs 다른 음) + 2단계(서로 다른 음끼리, 예: 미 vs 솔 비교) 신규.
- 각 spec은 동일 trial 로깅 API를 재사용하고, breadth 분석을 위해 공통 비율(2:3 등)을 의도 배치한다.
